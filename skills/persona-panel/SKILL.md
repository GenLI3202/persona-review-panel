# 人物评审团

让几位人物各自独立审同一份材料，再由你（主会话）汇总。价值在**分歧**：几个人都说的通常是显而易见的问题，一个人坚持而另一个人反对的地方，才是真正需要用户做决定的地方。

## 评审员名单

| 人物 | agent 名 | 最擅长审的 |
|---|---|---|
| 乔布斯 | `jobs-reviewer` | 产品定义与聚焦、端到端体验、设计品味、发布叙事 |
| 马斯克 | `musk-reviewer` | 成本结构、第一性原理、工程可行性、该删掉的东西 |
| 费曼 | `feynman-reviewer` | 是真理解还是只会命名、自欺、解释清晰度、证据 |
| Karpathy | `karpathy-reviewer` | AI/LLM 方案可靠性、工程现实主义、AI 炒作判断 |
| Ilya Sutskever | `ilya-reviewer` | AI 研究方向与品味、scaling 与泛化、安全风险 |
| 张一鸣 | `zhang-yiming-reviewer` | 产品与增长、组织与人才、全球化、长期决策 |

## 流程

### 1. 确定材料和问题
- **材料**：文件路径、目录、URL 或用户贴的文字。
- **问题**：用户想让评审团判断什么（例如「值不值得做」「最大的风险是什么」「怎么砍到 MVP」）。用户没说时，默认问题是「这份材料最致命的问题是什么，该怎么改」。
- 两者有一项实在无法确定时，问用户一次，不要猜。

### 2. 选人
- 用户点了名就用用户点的。
- 没点名：按上表挑与材料最相关的 **3 位**，并在一行里说明挑了谁、为什么。
- 最多 6 位。每多一位，大约多 1 万多 token 的人设加上一次材料阅读。

### 3. 写一份所有人共用的 brief
评审员**看不到当前对话**，brief 必须自足：
- 材料的位置（用绝对路径），或材料全文（用户贴的文字要原样放进 brief）。
- 必要背景：这是什么、给谁用、处在什么阶段、有什么约束。
- 要判断的问题。
- 一句提醒：按你的 agent 定义里的输出格式回答。

所有评审员拿到**同一份** brief。不要把一位评审员的结论喂给另一位。

### 4. 并行派出
- **Claude Code**：在同一条消息里为每位评审员各发一个 Agent 调用，`subagent_type` 填上表的 agent 名，`prompt` 填 brief。它们会并行运行。
- **Codex**：为每位评审员各 spawn 一个自定义 agent，`agent_type` 填上表的 agent 名，并行运行，等所有人都返回后再汇总。不要用 full-history fork：fork 会继承父 agent 的类型，和 `agent_type` 冲突而报错；brief 本身已自足，不需要带上对话历史。

### 5. 汇总
你是主持人，不是第七位评审员：不要加入自己的人设，也不要替评审员补他们没说的观点。

```markdown
# 评审团结论：<材料名>

**评审员**：<名单>

## 一句话
<综合判断，一两句>

## 共识
<两位及以上都指出的问题，注明是谁>

## 分歧（最重要）
| 议题 | <评审员 A> | <评审员 B> | 分歧根源 |
|---|---|---|---|
| … | 立场 | 立场 | 两人哪个心智模型/前提不同 |

## 只有一位提出的独到问题
- <人物>：<问题>，为什么值得注意

## 建议的下一步
1. <最高杠杆的一步>（主要依据：<人物>）
2. …

## 评审员追问你的问题
<把各位的追问合并去重，列给用户回答>
```

规则：
- 分歧不要抹平成「各有道理」。写清楚各自的立场，以及要用户拍板的是什么。
- 某位评审员说材料不足、无法判断的，如实列出他缺什么。
- 引用评审员的话时保持原意，不要把一位的观点归到另一位头上。

## 追问
用户想继续追问某一位时：Claude Code 用 SendMessage 发给那位评审员的 agent，延续它的上下文；Codex 在那位评审员的 agent 线程里继续发消息。想和某位人物深入长聊，就直接用对应的 perspective skill，不要再走评审团。
